# 聲音錄音與上傳功能實作報告

**主旨：ESP32 聲音錄音、SD 卡暫存與伺服器上傳功能說明**

您好：

以下說明目前 ESP32 聲音錄音與上傳功能的設計與測試結果。

## 一、錄音週期與音訊格式

- ESP32 每 10 分鐘執行一次錄音。
- 每次錄音時間為 5 分鐘。
- 音訊格式為 WAV、PCM、單聲道、16 kHz、16-bit。
- 依目前設定計算，5 分鐘音訊資料大小約為 9,600,000 bytes，加上 44 bytes 的 WAV header 後約為 9.6 MB。原先所述的 4.8 MB 並不符合目前 16-bit 音訊設定，已予以修正。

## 二、錄音資料處理架構

錄音期間由兩個 FreeRTOS task 平行處理：

- `capture_task`：讀取 I2S 麥克風資料，將 32-bit 輸入轉換為 16-bit PCM，並將資料放入固定大小的 audio block pool。
- `writer_task`：從 FreeRTOS queue 取出已完成的 audio block，套用音量增益後寫入 SD 卡 WAV 檔案。

此設計讓 I2S 取樣與 SD 卡寫入分開執行，可降低 SD 卡寫入延遲對即時取樣的影響。資料傳遞使用固定大小的 block pool 與兩條 FreeRTOS queue，分別管理可用 block 與已填滿 block，避免錄音過程中持續動態配置記憶體。

## 三、SD 卡檔案狀態管理

錄音開始時，系統會先在 SD 卡的 `undone` 資料夾建立暫存 WAV 檔案。錄音與 WAV header 完成確認後，檔案會由 `undone` 資料夾重新命名至 `done` 資料夾，代表該檔案已完成並等待上傳。

若錄音失敗、寫入失敗或裝置在錄音期間失去連線，檔案會保留在 SD 卡中，避免資料因網路或伺服器暫時不可用而遺失。

## 四、上傳與 ACK 驗證

ESP32 會從 `done` 資料夾找出最早的待上傳 WAV 檔案，透過 HTTP POST 上傳至 `server.py`。上傳請求會包含：

- 裝置 ID
- 錄音識別碼 `capture_id`
- 錄音時間
- 宣告的檔案大小

只有在下列條件都成立時，ESP32 才會視為上傳成功並刪除 SD 卡中的 WAV 檔案：

1. HTTP 回應狀態為 200。
2. Server 回傳的 `status` 為 `ok`。
3. 回傳的 `capture_id` 與 ESP32 上傳時提供的識別碼相同。
4. Server 回傳的檔案大小與本機檔案大小相同。

若連線失敗、Server 沒有回覆有效 ACK，或 ACK 內容不一致，該 WAV 檔案會繼續保留在 SD 卡，並於之後的上傳週期重新嘗試。

目前 `server.py` 會檢查 WAV 的 `RIFF/WAVE` 標頭與宣告的檔案大小；檔案會儲存於 PC 端。Server 目前尚未由 WAV header 計算並驗證錄音時間是否確實為 5 分鐘，因此「5 分鐘長度」是由 ESP32 錄音流程保證，而不是由 Server 完整驗證。

## 五、Heartbeat 狀態回報

ESP32 每 1 分鐘向 Server 發送一次 heartbeat 封包，內容包含：

- 裝置 ID
- 裝置回報時間與 uptime
- Wi-Fi 連線狀態與訊號強度
- 可用 heap
- SD 卡剩餘空間
- 待上傳檔案數量
- 成功或失敗的錄音與上傳統計
- 最近一次錯誤資訊
- 裝置 reset reason

這些資訊可讓 PC 端監控裝置是否在線、是否有待上傳資料，以及裝置目前的資源與錯誤狀態。

## 六、斷線與重啟時的資料保護

測試期間曾模擬 PC 斷電，造成 `server.py` 暫時關閉，以及 ESP32 重啟的情況。在 Server 無法連線期間，ESP32 無法立即上傳錄音檔案，但已完成的 WAV 檔案會暫存在 SD 卡的 `done` 資料夾中。

當 PC 端 Server 恢復運作，且 ESP32 重新建立網路連線後，ESP32 會先處理 SD 卡中先前尚未上傳完成的檔案。只有收到 Server 有效 ACK 後才會刪除本機檔案，完成後再繼續執行後續的錄音與上傳週期。因此，短時間的 Server 關閉不會直接造成已完成錄音檔案遺失。

## 七、目前測試結果

目前已將 ESP32 放置於實驗室 Wi-Fi 環境連續測試約 2 天，PC 端執行 `server.py` 接收資料並儲存於 PC。測試期間，只要 Wi-Fi 與 Server 維持正常連線，系統即可持續執行錄音、檔案儲存、上傳與 ACK 驗證流程。

目前尚未觀察到錄音、SD 卡暫存、Server 接收或上傳確認流程出現異常。後續仍可增加長時間斷線、SD 卡容量不足、Server 重複收到同一檔案，以及不同網路環境下的壓力測試，以進一步驗證系統的容錯能力。

以上為目前聲音錄音與上傳功能的設計及測試結果，謝謝。
