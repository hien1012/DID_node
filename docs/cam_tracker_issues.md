# 相機節點：Stage2 追蹤器待修問題

2026-11-12 整理，還沒修改。對象是 `infer_node/` 相機節點（`INFER_ROLE_CAM`）。

## 目前的流程

1. 每一幀 FD 找出所有框（`vision/fd_mix.c`，320×240 處理，框換回 640×480）。
2. `stage2_update_core()`（`vision/stage2.c`）把框配對到現有 track：
   - 預測位置 = 上次中心 + 速度（IIR 平滑，`v = (3v + new_v) / 4`）
   - 曼哈頓距離 ≤ `max_match_dist`，面積比在 `area_ratio_min..max` 之間才算候選
   - 依距離排序後 greedy 一對一配對
3. 配對成功：`age++`、`miss = 0`。沒配到：`miss++`，`miss > max_miss` 就刪掉 track。
   沒配到 track 的框開新 track，`age = 1`。
4. `age >= age_threshold` 且還沒送過（`cnn_sent == false`）→ 用這一幀的框送 CNN，只送一次。
   沒有空的 frame_job 時延到該 track 下一次配對成功；送出前就被刪掉的記入 `expired`。

目前參數（`cam_infer.c:2057-2065`）：

| 參數 | 值 |
|---|---|
| `max_match_dist` | 240 px（全解析度，曼哈頓距離） |
| `max_miss` | 2 |
| `age_threshold` | 3 |
| `area_ratio_min / max` | 0.30 / 3.00 |
| tracker reset | 只在開機 `stage2_init()` 一次，之後不 reset |

## 問題

### 1. `age` 是累計配對次數，不是連續次數

- 位置：`stage2.c:397`（配對成功 `age++`）、`stage2.c:718-728`（沒配到只有 `miss++`，age 不歸零）。
- 行為：只要中間沒有連續漏掉 3 幀，就會一直累計。例如 `● ○ ○ ● ○ ● ` 在第 6 幀送出。
  每次配對成功都把 `miss` 歸零，所以理論上可以每 3 幀才配中一次，最後還是會送。
- 要決定的事：設計上是要「連續 3 幀」還是「累計 3 次」。如果要連續，沒配到時 `age` 也要歸零（或改成另一個連續計數）。

### 2. 雜點也可能累計到 3 次被送進 CNN

- 來源：
  - FD `bbox_thresh = 0`（`cam_infer.c:2047`），1 個像素的連通區也會變成框；refine 只丟掉 ROI 內完全沒有 Sobel 邊緣的框。
  - 加上問題 1 的累計規則，同一區域反覆閃爍的雜點（樹葉、水面反光、閃爍光源）可以湊滿 3 次。
- 可能的修法（擇一或組合）：
  - `bbox_thresh` 設下限（低解析度像素數），先濾掉極小的框
  - 要求連續配對（見問題 1）
  - 要求累計位移超過某個量才送（靜止閃爍的雜點中心幾乎不動）
  - 固定雜訊區域的 exclusion mask

### 3. `max_match_dist = 240` 太寬

- 240 px 約是畫面寬（640）的 37%；5 fps 下等於允許目標一幀移動 240 px。
- 風險：兩個靠近的目標、或一個目標和附近的雜點，可能被配到錯的 track（greedy 只看距離誰近）。
  配錯會讓 track 的框跳到雜點上，送進 CNN 的 ROI 就不是原本的目標。
- 可能的修法：門檻改成跟框大小成比例（例如 `k × max(w, h)`，再設上下限），或先用實際錄影的 track 位移分布決定一個較小的固定值。

### 4. 目標停下再動會被重複分類

- 原因：FD 是幀差，目標靜止時就沒有框；連續 3 幀沒配到，track 被刪掉（`max_miss = 2`）。
  目標再動時開新 track，`cnn_sent` 重新是 false，3 次配對後再送一次 CNN。
- 影響：同一個目標可能被分類很多次（CNN 負載、回報量增加；server 端看起來像多個目標）。
- 可能的修法：
  - 已送過 CNN 的 track 用較長的 `max_miss`（多保留幾秒），讓它在原地等目標再動
  - 保留最近刪掉的 track（位置 + 結果 + 時間），新 track 出現在附近時繼承結果，不再送 CNN

### 5. 速度估計：整數截斷讓預測偏慢，漏幀時沒有往前推

- 位置：`stage2.c:389-392`（`v = (3v + new_v) / 4`，int 除法向 0 截斷）、`stage2.c:718-728`（沒配到時 cx / cy / v 都不動）。
- 整數截斷：
  - 每幀移動 < 4 px 時 `v` 永遠是 0（`(0 + 3) / 4 = 0`）。
  - 等速 10 px/幀時 `v` 依序是 2 → 4 → 5 → 6 → 7，然後停在 7（`(21 + 10) / 4 = 7`），永遠追不到 10。
  - 新 track 的 `v = 0`，第一次配對只取 1/4 位移，前幾幀預測落後最多。
- 漏幀：沒配到的幀不更新位置，下一次配對時預測仍是「最後中心 + 1 幀的 v」，但目標已經走了 2–3 幀；
  配上後 `new_v` 是多幀的位移，卻被當成一幀的速度。
- 影響：預測誤差要靠很大的 `max_match_dist` 吸收，這可能就是目前要開到 240 的原因（問題 3）。
- 可能的修法：速度用定點數（例如 ×16）或 float；沒配到時把預測位置往前推一步（`cx += vx`），
  或記錄上次配對的 frame_idx，配上時 `new_v` 除以間隔幀數。

### 漏幀（track 這一幀沒配到）的來源

| 類別 | 原因 | 位置 |
|---|---|---|
| FD 沒框 | 目標停下或移動太少，幀差 ≤ 30 | `fd_mix.c:394` |
| | 目標太小，nearest ×2 下採樣後只剩幾個像素，膨脹後也連不起來 | `cam_infer.c:1410` |
| | refine：ROI 內沒有 Sobel 邊緣 > 100（低對比、模糊）→ 整個框丟掉 | `fd_mix.c:359` |
| | NMS：和較大的框有一點重疊（IoU > 1e-4）就被丟掉 | `fd_mix.c:669` |
| | 雜點多時 contour 由上往下掃到 100 框就停，畫面下方的目標沒被掃到 | `fd_mix.c:510` |
| 有框但沒過 gate | 距離 > 240：速度預測偏差（問題 5）或目標突然加速 | `stage2.c:662` |
| | 面積比不在 0.3–3：目標被切成兩塊（單色目標幀差只剩前後緣）、和別的區域連成一塊 | `stage2.c:659` |
| 被搶走 | greedy 時框離另一條 track 的預測更近，被那條先配走 | `stage2.c:689` |

相機丟幀（queue 滿、`dropped=`）不算漏幀：那一幀沒進 `detect_frame()`，tracker 根本沒被呼叫，`miss` 不變；
但下一幀的幀差和位移是隔兩幀的量。

## 相關的 FD 行為（修追蹤器時一起看）

- NMS 的 IoU 門檻是 `1e-4`（`cam_infer.c:2048`、`fd_mix.c:669`）：兩個框只要有一點重疊，小的就被丟掉，不會合併進大的。
  一個目標被切成兩塊時，留下的是較大那塊，不是兩塊的聯集。
- flood fill 堆疊到上限（w×h 點）時只保留走過的部分（`fd_mix.c:449`），整片畫面變化時框可能不完整。
- 每個連通區都 malloc / free 一次 flood fill 堆疊（`fd_mix.c:409`），雜點多時次數跟著變多。

## 修改前要先量

  每條 track 的配對序列（連續或間斷）、每幀位移、被送 CNN 的 track 中有多少是雜點。
- 板上看 `Camera:` 統計的 `rois=` / `expired=`，以及 server 端每分鐘 ROI 數，修改前後對照。
