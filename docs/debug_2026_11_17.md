## 1. 推論中 task watchdog：IDLE (CPU 1) 沒有餵狗

### 現象

推論進行中（開機約 96 s）出現：

```
E (95971) task_wdt: Task watchdog got triggered. The following tasks/users did not reset the watchdog in time:
E (95971) task_wdt:  - IDLE (CPU 1)
E (95971) task_wdt: Tasks currently running:
E (95971) task_wdt: CPU 0: cam_infer
E (95971) task_wdt: CPU 1: cam_detect
```

CPU 1 backtrace：

```
fd_roi_refine           vision/fd_mix.c:323     （ROI 內掃 edge mask 找連通區的雙層迴圈）
fd_process_frames_gray  vision/fd_mix.c:893
run_frame_difference    cam_infer.c:1456
detect_frame            cam_infer.c:1700
cam_detect              cam_infer.c:1786
```

### 分析

- 被抓的是 **IDLE1 連續 5 s 沒跑**（`CONFIG_ESP_TASK_WDT_TIMEOUT_S=5`、`CHECK_IDLE_TASK_CPU1=y`），不是 `cam_detect` 卡死。
- `CONFIG_ESP_TASK_WDT_PANIC` 未開 → 只印警告、不重開機，推論會繼續。
- `cam_detect`（Core 1，優先權 5）只在 `s_ready_queue` 空時才阻塞。畫面變化大時（光線變化、枝葉晃動）
  frame difference 產生很多框，ROI refine 對每個框做 Sobel + flood fill，**單幀 FD 超過幀間隔 200 ms（5 fps）**
  → queue 一直有幀 → `cam_detect` 吃滿 Core 1 → IDLE1 餓死。
- backtrace 停在 `fd_roi_refine` 只代表時間花在那裡。flood fill 會把走過的像素標成 128，每次一定結束，排除無窮迴圈。
- 可能加重 refine 成本的設定：
  - `roi_refine_min_cc_area = 0`（`cam_infer.c` 的 FD 參數）：1 像素的 Sobel 雜訊也各做一次 flood fill。
  - `fd_flood_fill_optimized()` 每次呼叫都在 PSRAM `malloc` / `free` 8 KB stack（`fd_mix.c:409`），小連通區多時每幀上千次。

### 解法（已改，上板跑過一次）

`infer_node/main/cam_infer.c` 的 `cam_detect` 迴圈結尾（約 1795–1802 行）：

```c
if (uxQueueMessagesWaiting(s_ready_queue) > 0U) {
    vTaskDelay(1);
}
```

- 有積壓才讓出 1 tick（`CONFIG_FREERTOS_HZ=100` → 10 ms）給 IDLE1；沒積壓時下一次 `xQueueReceive` 本來就會阻塞，不多花時間。
- 這只解決 WDT，**不會讓 FD 變快**：大變化場景下仍會跟不上 5 fps，`camera_capture` 會印 `Ready queue full ... dropped=`。

### 待確認 / 後續

- [x] 上板：跑到約 214 s 沒有再出現 WDT（原本約 96 s 出現）。
- [x] stage 表（300 幀）：`fd` avg/max = 136.3/257.2 ms、`refine` 66.0/151.7 ms；之後 76.5/230.4、20.5/132.1 ms。
  `detect` max 263 ms > 200 ms，但 `queue` max 103 ms、`dropped=0`：大變化時短暫落後、之後追得上。
  refine 是 FD 中最大的一段，但目前沒有丟幀，加速先不做。
- [ ] 若要讓 FD 跟上，可考慮：
  1. `roi_refine_min_cc_area` 調到 4–8，砍掉大量雜訊連通區（refine 後的框可能略有差異）。
  2. `fd_flood_fill_optimized()` 改用只增不減的 static stack 重複使用，省掉每次的 PSRAM alloc/free
     （FD 只由 `cam_detect` 呼叫，static 安全）。

## 2. 相機統計出現 1 次掉幀（gaps=1）

### 現象

```
Camera: frames=300 processed=300 dropped=0 gaps=1 incomplete=1 stale=1 ... interval=199842..399842 us
```

900 幀時仍是 `gaps=1 incomplete=1 stale=1`（累計值），之後沒有再增加。

### 分析

- `interval` max ≈ 400 ms = 2 個週期 → 剛好少 1 幀。
- `dropped=0`：不是 FD 跟不上；`incomplete=1`：驅動收到長度不符的幀（`cam_hal.c:478-480`，`len != fb_size`）直接歸還，
  `camera_capture` 拿不到 → 兩幀間隔 400 ms。
- 原本推測是 resume 時從半幀開始收，但 `infer_node` 全程不停 XCLK（`cam_infer_pause()` 只呼叫 `cam_stop()`，
  關 VSYNC 中斷與 DMA；真正停 XCLK 的 `cam_record_set_xclk_output()` 只有 `main/` 使用），而 `cam_start()`
  開 VSYNC 中斷前會先清掉 pending 中斷（`ll_cam.c:376`），DMA 應從幀邊界開始。所以也可能是運作中偶發的匯流排錯誤，
  單憑統計分不出來。

### 處理

`cam_infer.c` 的 `camera_capture`（`gaps++` 處）加上 log，記錄發生在第幾幀：

```
W (...) cam_infer: Frame gap before frame N: interval=... us gaps=... incomplete=... stale=...
```

- gap 在 frame 1 → 啟動造成；在運作中 → 看 `incomplete` 有沒有同時增加
  （有 = PCLK/資料線收到短幀；沒有 = 感測器或 VSYNC 沒送幀）。
- 之後一次執行：`gaps=0 incomplete=0 stale=2 interval=199854..199986 us`，沒有再發生。

## 3. 非背景的推論結果也存 SD（移植 ESP32 版設計）

原本只存低信賴度（預測類別機率 < `INFER_LOW_CONF_THRESHOLD`），信賴度高的 drone / helicopter 只回傳結果、不留原始資料。
依 `ESP32_cam_mic/infer_node` 的做法改成「低信賴 **或** 非背景」就存：

- `infer_config.h`：`INFER_SAVE_NON_BACKGROUND`（S3 預設 1；ESP32 版預設 0）、`INFER_BACKGROUND_LABEL "background"`。
- `sample_store.c`：`sample_store_find_background()` 開機時依名稱找背景類別（audio 是 0、video 是 2，不寫死索引），
  `sample_store_save_reason()` 產生 meta 的 `save_reason`：`low_conf` / `non_background` / `both`。
- `mic_infer.c`：非背景視窗也交給 `audio_writer`；log 尾巴多 ` DET`。
- `cam_infer.c`：一幀有一個非背景 ROI 就存整幀。
- 統計的 `low` 只算低信賴，開啟後 `saved` 會大於 `low`。
- 上板確認：伺服器收到的樣本 meta 已有 `save_reason`（見下一節的樣本）。

## 4. 麥克風節點的推論結果與 PC int8 TFLite 不一致 → ESP-NN 的 S3 avg pool 組語錯誤

### 現象

節點辨識結果和 PC 上用同一個 `logmel_cnn_classifier_int8.tflite` 跑同一個 WAV 的結果很多不同。

### 1) 先確認前處理、模型與訓練一致

- `logmel_features_int8.c/.h` 與 `TTGO_I2S_Record_Test/main` 逐位元組相同（SHA256）。
- I2S 設定、PCM 轉換 `(int16)(raw32 >> 16) × 30` 飽和、500 ms 暖機丟棄、2 s 視窗都與 `app_audio_stream_int8.c` 相同。
- 模型：S3 內嵌的位元組 SHA256 = `961ef794…` = `cnn_output/logmel_cmvn/0909_outdoor/inmp/…int8.tflite`
  （TTGO `main` 目前放的是 `pdm` 模型 `2d41ad19…`，與 S3 不同是因為麥克風不同）。
- Mel 頻帶 250–2500 Hz：用 `log_mel_features.mel_filter_bin_edges()` 的公式重算 34 個 bin 邊界，與
  `preprocess_config_int8.h` 的 `g_audio_mel_bin_edges` 完全相同。
- CMVN（每 band 對時間、母體 std、std 下限 2.0 dB）與全域正規化 `(x − mean) / (std + 1e-6)` 與 `logmel_cnn.py` 相同。

### 2) 用伺服器上的樣本比對：兩次開機結果完全不同

對 `server_mix/node-s3-B81F3FCFAF50` 每個 `.wav` 以訓練用前處理 + int8 TFLite 推論，與 meta 的 `probs` 比較：

| 開機 | meta `invoke_us` | 節點輸出 | 與 PC（inmp）比較 |
|---|---|---|---|
| `_181_`（23:17–23:19，18 個） | **≈ 57 ms** | helicopter 永遠 0.000，bg/drone 都在 0.36–0.64 | argmax 大多不同 |
| `_960_`（23:20 之後） | **≈ 1034 ms** | 正常分布 | 6/6 一致，機率差 ≤ 0.02 |

`invoke` 快 18 倍且輸出擠成均分 → 第一次開機是 ESP-NN 版本。
`infer_node/build/CMakeCache.txt` 為 `ESP_NN_KERNEL_SET:STRING=all`、`build_debug` 為 `none`；
`ESP_NN_KERNEL_SET` 是 CMake cache 變數，一個 build 目錄下過一次 `all` 之後會一直沿用。

### 3) 逐層 dump 定位

使用者以 `idf.py -B build_debug -DINFER_AUDIO_DEBUG_DUMP=1 -DESP_NN_KERNEL_SET=all build flash`，
再用 `TTGO_I2S_Record_Test` 的 `tools/receive_infer_node_dump.py --port COM14 --reset` 與
`compare_infer_node_debug_dump.py --dump-dir infer_node_dump` 比對：

- 前處理全部 OK，量化後 int8 輸入與 PC 完全相同（0/3968）。
- op00–op06（`CONV_2D` ×3、`MAX_POOL_2D` ×2、`DEPTHWISE_CONV_2D` ×2）`max_diff=0`。
- **op07 `AVERAGE_POOL_2D`（1×8×31×48 → 1×8×1×48）`max_diff=253`、336/384 不符**；op08–op10 跟著錯。
- 同一輸入 `device_live = [0.754, 0.246, 0]`、`device_dump_interpreter = [0, 0.996, 0]`，兩次結果不同。

### 原因

`kernels/esp_nn/pooling.cc` 在 channels % 4 == 0 時呼叫 S3 組語 `esp_nn_avg_pool_s8_esp32s3_asm`（48 channels 符合）。
這個組語在本模型的 op07 輸出錯誤且不穩定。另外注意到它 `entry a1,240`、9 個參數在 a1+240..275，
卻有 `s32i a13,a1,280` 寫到 frame 與參數區之外，可疑但未完整追完。

### 解法（已上板驗證）

`infer_node/components/tflite-micro/tensorflow/lite/micro/kernels/esp_nn/pooling.cc` 的 `AverageEvalQuantized()`：
組語分支改成 `if (false && depth % 4 == 0)`，int8 avg pool 一律走 `esp_nn_avg_pool_s8_ansi()`
（捨入 `(sum ± cnt/2) / cnt` 與 TFLM reference 相同）。其他 ESP-NN kernel 照用。

11/18 重跑 dump：op00–op10 全部 `max_diff=0`，`device_live`、`device_dump_interpreter`、
`pc_cnn_on_device_input`、`pc_end_to_end` 都是 `[0.992188, 0.007812, 0.0]`。

11/18 以 SD 重播（第 6 項）在**同一個輸入**上對照確認：暫時把 `pooling.cc` 改回組語版，重現錯誤（op07 起不符，
正式結果與 dump interpreter 也不同）；恢復 C 版後所有層與 PC reference 逐位元相同。
**確定是 S3 組語 avg pool 造成，改用 C 版即可解決。** 數據見第 6 項的上板結果。

## 6. SD 重播四方比對（11/18 新增，已上板）

即時 dump 的問題：兩次燒錄（ESP-NN / reference）抓到的輸入一定不同，無法在同一個輸入上比較兩種 kernel；
而且抓到什麼看運氣（多半是 background）。改成從 SD 讀固定輸入。

- kernel 是編譯時決定的（`components/tflite-micro/CMakeLists.txt` 以 `esp_nn/*.cc` 取代 reference 的 `.cc`），
  同一個韌體不能同時有兩組，所以兩種 kernel 各燒一次、各收一次，不改 tflite-micro。
- 韌體（`INFER_DEBUG_REPLAY=1`，`main/debug_replay.c`）：開機（Wi-Fi、校時、pipeline init、SD 掛載）後不啟動即時推論，
  讀 SD 的 `debug/in/`：相機 `cam_<名稱>.gray`（64×64 uint8，剛好 4096 B）、麥克風 `mic_<名稱>.wav`
  （16 kHz mono PCM16，≥2 s，只用前 2 s），另一角色的檔案略過，依檔名排序，最多 32 個。
  每個檔案：正式 interpreter 推論 → 既有的 `cam_debug_dump_roi()` / `audio_debug_dump_window()` 輸出。
  dump 名稱 `<檔名>_<ESP_NN_KERNEL_SET>`（例如 `cam_drone01_all`）；meta 的 `source` = `sd_replay`、`input_file` = 檔名。
  重播完板子停住，不回到即時推論。
- 音訊 meta 新增 `kind: "audio_window"` 與 `esp_nn_kernel_set`（之前只有相機有）。
- PC：`tools/make_debug_inputs.py` 由圖片（灰階、縮成 64×64）、WAV（混成 mono、重取樣 16 kHz、取 2 s）
  或既有 dump（`roi.gray` / `input.wav` 原樣複製）產生輸入檔。
- PC：`tools/compare_debug_dumps.py`（取代 `compare_cam_debug_dump.py`，相機與音訊共用），依 `input_file` 把兩個 build 的 dump 配對：
  - 逐層：每個 node build 各自對 PC C++ reference（`BUILTIN_REF` + preserve_all，輸入 = 節點自己的 CNN 輸入），再加一欄 node 對 node。
  - 機率：node ESP-NN、node TFLM reference、PC C++ reference、PC Python int8.tflite（預設 kernel）。
    正式重跑 / dump interpreter 只在與正式結果不同時列為 finding。
  - 音訊另比前處理：節點 C 的 `fe_mel_power` / `fe_log_mel` / `fe_cmvn` / `fe_normalized` / `fe_quantized*` 對

    參數讀模型旁的 `preprocess_config.json`），並列 PC Python end-to-end（input.wav → Python logmel-CMVN → int8.tflite）。
  - 預設模型（已確認與韌體內嵌的 flatbuffer 逐位元組相同）：相機 `DID_CAM_SEAN/CNN/quantize_out/model_int8.tflite`，
    音訊 `TTGO_I2S_Record_Test/cnn_output/logmel_cmvn/0909_outdoor/inmp/logmel_cnn_classifier_int8.tflite`。
- 已在 PC 驗證：
  - 用既有的即時 dump 跑新腳本：相機兩筆 20 層全 exact；
    音訊 11/17 修正後的兩筆 11 層全 exact，**節點 C 前處理與 Python 訓練前處理的 int8 輸入逐位元相同**

  - 把同一筆 dump 複製成 `_all` / `_none` 一對、在 `_none` 的 op16 改 1 個值：配對、node 對 node 欄、first failure 都正確。

### 上板結果（11/18）

SD 上的輸入：`cam_background0.gray`、`mic_drone0.wav`。dump 與比對結果在 `infer_node/replay_dump/`

- C 版 avg pool：node ESP-NN、node reference、PC C++ reference 三者機率完全相同，VERDICT 為
  `all node builds match the PC reference at every layer`。
- PC Python int8.tflite（預設最佳化 kernel）差 1/256，是 PC kernel 自己的捨入，不是節點的問題：
  mic `[0.832, 0.156, 0.012]`，cam `[0, 0.0039, 0.9961]`。
